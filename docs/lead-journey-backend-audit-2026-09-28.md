## Durable intake: success, rejection, retries and duplicates

- [API](../src/app/api/leads/route.ts) bounds JSON bodies to 64 KiB, checks origin/honeypot/readiness, normalises input and calls [service](../src/lib/lead-intake/service.ts). `/api/funnel` delegates to the same handler. Production readiness is **configuration presence only**: `LEAD_INTAKE_ENABLED`, `DATABASE_URL`, `LEAD_RATE_LIMIT_SECRET` in [security](../src/lib/lead-intake/security.ts); it does not probe schema or downstream services.
- [Contract](../src/lib/lead-intake/contract.ts) validates exact fields, current privacy acknowledgement, separate optional marketing choices and compatible versions. Fresh non-legacy submissions require the current version; old-version retries can return an existing receipt. Legacy payloads remain accepted through explicit normalisation and do not acquire marketing consent.
- [Persistence](../src/lib/lead-intake/persistence.ts) atomically saves a Lead, any subscription/consent records and two separate destination events (`notification`, `google_sheets`) in a serializable transaction. Advisory locks and a per-IP-HMAC limit of ten submissions per ten minutes protect intake; concurrency conflicts receive bounded retry.
- A committed new submission returns 201 with `leadId`, `submissionId`, `status=created`; an identical repeated reference returns 200 `duplicate` without creating another lead, consent event or delivery pair. The same reference with changed normalised content returns 409. Deduplication is by submission ID, **not by email**: a genuine new enquiry from the same person is another Lead.
- Invalid fields/project return 400, bad production origin 403, throttling 429 with `Retry-After`, missing/failed infrastructure 503, unexpected failure 500. A failed transaction does not claim receipt. Sanity lookup failure during property resolution is infrastructure failure; draft/unpublished/missing properties are rejected by [project resolver](../src/lib/lead-intake/project.ts).
- Immediate delivery failure does not undo a successfully saved enquiry. API success means **saved**, not emailed or exported. [Shared client](../src/lib/lead-intake/client.ts) requires a matching structured receipt, preserves the reference after ambiguous failure and creates a new reference when the payload changes.
- **Client inconsistency to fix:** `LeadEoiForm` and `EnquiryForm` bypass that shared retry helper and keep their submission reference after edits. Following a save whose response was lost, an edited retry can therefore hit 409. `EnquiryForm` explains the conflict; `LeadEoiForm` currently gives a generic check/retry message. Align behaviour without silently duplicating the original enquiry. A page refresh/closed modal also loses in-memory draft/reference state.

## Delivery: independent destinations, not a CRM

- [Runtime](../src/lib/lead-delivery/runtime.ts) selects notifications whenever global delivery is on and Sheets only when `LEAD_SHEETS_ENABLED=true`. There is no clean notification-off switch. Both events are created even while delivery is disabled, so activation must review pending historical jobs.
- [Worker](../src/lib/lead-delivery/worker.ts) and [repository](../src/lib/lead-delivery/prisma-outbox.ts) use atomic claims, leases, exponential retry and dead letters. Defaults: 20 events/run, eight attempts, ten-minute stale lease; [Railway worker](../railway.worker.json) schedules a bounded batch every five minutes. One destination failing does not resend the other successful destination.
- [Resend transport](../src/lib/lead-delivery/resend.ts) is staff-only, uses a stable event idempotency key and refuses ambiguous retries after its conservative 23-hour retry boundary. Its `DELIVERED` status means provider acceptance; it does not establish inbox arrival. Provider delivery/bounce webhooks are not wired into this outbox.
- [Sheets transport](../src/lib/lead-delivery/google-sheets.ts) validates exact 23 headers, checks event ID and appends RAW values. It does not create the tab. Read-then-append is not an atomic uniqueness guarantee; reconcile ambiguous append timeouts before manual replay. Do not use the native Form's response tab for this adapter.
- [Payload](../src/lib/lead-delivery/payload.ts) exports `status="New"`, `owner=""`; these are not assignments or a synchronised CRM workflow. No CRM adapter or customer campaign destination was found in current runtime/schema. Existing `MessageThread`/`Message` schema and mock message data do not provide the missing operational integration.

## Budget and property context: where information is absent or lost

1. V2 `preferences` only accepts market, location, property type, bedrooms, bathrooms and timeframe. Adding budget/currency/period client-side today is rejected as an unknown key. `Lead.budget` only receives the legacy budget field; modern quiz/interiors budget survives as notes instead. The homepage service wizard's budget and all other answers are currently lost entirely.
2. A property slug sent through the common form **is saved correctly** as `Lead.projectSlug`, with a server-resolved title/community. It is also included in property-match subscription criteria. However, staff/Sheets payload includes only the project **title**, not slug/canonical URL; `/register-interest?project=…` becomes the query-free landing path. Add an explicit property reference/link for reliable downstream matching.
3. [Normalisation](../src/lib/lead-intake/normalize.ts) intentionally strips project/preferences when interest changes to `general_enquiry`. If a visitor is asking a general question about a specific property, decide how the intended context should remain visible without silently carrying irrelevant hidden filters.
4. Budget persistence needs explicit minimum/maximum, original currency and rental period, with display conversions kept separate. The current listing search's budget calculations are not an enquiry data contract. A received budget must not become an invented property asking price.
5. Property-match criteria are one record per email and a later opt-in **replaces** the previous criteria. There is no saved-search collection or browsing-history profile. Decide whether multiple active interests are required before implementing matching reminders.

## Withdrawal and the proposed next-day reminder

- [Newsletter withdrawal](../src/lib/lead-intake/newsletter.ts) and [property-match withdrawal](../src/lib/lead-intake/property-match.ts) atomically set `WITHDRAWN` and append wording/version/time evidence while protecting against stale updates. Search found definitions/exports/tests only: no public handler calls them. Unchecking a later form's optional box is not implemented as withdrawal; explicit later opt-in can reactivate that purpose.
- No customer reminder queue exists to cancel today. With a CRM/email platform, synchronise withdrawal/suppression promptly and cancel pending marketing there; recheck current purpose-specific consent and suppression at send time and retry time. Cancelling nurture must not delete the enquiry or block staff responding to the request.
- [Analytics](../src/lib/analytics.ts) intentionally excludes contact details, budgets, search text and user IDs; it gates tracking by analytics permission. GA4 receipt cannot identify which email address should receive a property reminder. Do not repurpose that measurement stream or silently broaden newsletter permission into browsing-based targeting.
- A proposed 24-hour reminder requires: a known/confirmed subscriber, separate approved permission for using identified browsing, first-party allowed property-view events, a defined eligible last-activity time, deduplicated scheduling and a connection to the chosen email platform. Skip anonymous/declined visitors. Pause/cancel on withdrawal, a new relevant visit if the rule is inactivity-based, completed enquiry, manual agent handling or unavailable/unpublished property; settle these business rules with Sonia.
- Prefer a basic opted-in **brief-based** matching pilot before behaviour-based reminders. Reuse an existing suitable CRM/email platform's scheduling/unsubscribe/suppression; keep the website consent/event integration explicit. Custom scheduling infrastructure is an alternative only if a material requirement demands it.
