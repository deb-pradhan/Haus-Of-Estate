## Shared behaviour

- The main layout calls `isLeadIntakeReady()`: intake flag + nonblank database URL + production rate-limit secret. These are configuration-presence checks, not proof of connectivity/delivery. When false, no automatic popup mounts; legacy modal actions navigate to `/enquire`, which shows the unavailable/email page. Sources: `src/app/(main)/layout.tsx`, `src/lib/lead-intake/security.ts`, `src/components/lead-modal/modal-context.tsx`.
- Canonical EOI/question forms post JSON to `/api/leads`. The server validates consent/origin/project and confirms success only after saving the Lead, consent evidence and separate `notification` / `google_sheets` outbox events. Their UI validates the saved receipt; it does not prove Sheet/inbox arrival. The separate homepage `ServicesToggle` exception above must be removed before release. Lead customer acknowledgements and marketing campaigns are not connected. Sources: `src/app/api/leads/route.ts`, `src/lib/lead-intake/{contract,persistence,client}.ts`.
- The three-step EOI form collects name/email/optional phone + privacy acknowledgement first, intent second, then optional property preferences/message and separate email choices. Advancing a step does **not** save a partial lead. Both marketing choices start false; ordinary enquiries require neither. Newsletter-only needs its explicit newsletter choice. Source: `src/components/lead-eoi/lead-eoi-form.tsx`.

## Context and privacy findings

1. **Property slug is already supported**, not missing universally: detail CTAs and `register-interest?project=` preserve it and the server rejects unpublished/unknown project submissions. Direct `/enquire`, generic advisor links, external contact and search-empty CTAs lack it. The project delivery label can be resolved server-side; do not trust a title/price supplied from a URL as authoritative.
2. **No structured budget in the shared lead schema.** `preferences` permits market/location/type/bedrooms/bathrooms/timeframe only. Interiors and quiz place budget text in `contact.message`; standard EOI has no budget input. No currency, price range, rent period, search keyword/category or exact CTA identifier is recorded as a dedicated lead field. Source: `src/lib/lead-intake/contract.ts`, `src/components/lead-eoi/types.ts`.
3. **Greece selection mismatch:** catalogue navigation supports Greece but EOI country choices and inference omit it. Existing options are UK/UAE/Indonesia/Cyprus/Other. Property slug still survives, but visitors cannot select Greece explicitly in the country menu. Source: `lead-eoi-form.tsx`.
4. **Attribution is campaign landing context, not necessarily submission page.** `getLeadAttribution()` reuses current/last session UTM landing pathname; the payload has no separate current-page/CTA field. Referrer query/hash are stripped server-side; only named UTMs are captured. Do not put personal details in campaign tags. Sources: `lead-eoi/attribution.ts`, `src/lib/lead-intake/normalize.ts`.
5. **Enquiry private fields stay out of navigation/analytics.** Interiors links allowlist goal/room; contact/message/budget are posted in JSON. Analytics receives allowlisted event metadata, not form answers; page paths exclude query strings. Catalogue filters already use URL query parameters, including min/max price, so any future private budget brief must be passed separately. Sources: `src/lib/interiors-enquiry.ts`, `src/lib/analytics.ts`, `properties/property-search-form.tsx`.
6. **Retry preservation lasts only within the mounted form.** Failed EOI/question submissions retain fields and reference; closing/reloading discards them. EOI/question forms keep the same reference if edited after an ambiguous response, so a previously saved changed payload can conflict (question form explains refresh; EOI gives generic failure). Quiz/legacy helper generates a new reference when its payload changes. Sources: both canonical forms and `src/lib/lead-intake/client.ts`.

## Content and operational boundaries

Normal listing/detail queries use published content; authenticated editorial preview is a separate perspective, and draft/local property actions are disabled. Empty search results are explicit. Approved careers can use supplied title-only fallbacks, without fabricated descriptions. Source evidence establishes these rules, not which listings are currently published or available; no live CMS read was performed for this audit. Relevant queries: `src/sanity/queries.ts`; published enquiry recheck: `src/lib/lead-intake/project.ts`.

The independent Google Form/response tab is not wired into any website CTA by this code audit. Any new Form opt-ins or receipt behaviour being configured separately must be documented with fresh external evidence. Native Form submissions are not automatically website Leads.

## Priorities for the next implementation decision

1. Remove the homepage local-only success path and verify all mounted lead entry points respect the shared gate. Then verify hosted durable capture/delivery before opening public intake. Do not infer operational success from a click or provider acceptance.
2. Repair rental intent in footer/empty results, preserve search mode through property navigation, and carry an explicit property/service/CTA context through the existing form rather than creating duplicate forms.
3. Offer general/service enquiries from advisor/property-management CTAs, add Greece coherently, and agree the minimum structured budget/sell-versus-let/service fields before extending persistence/Sheet columns.
4. Decide external-channel logging, booking integration and careers persistence separately; none currently follows from the lead worker. Remove or approve unsupported response-time promises.
5. Define abandonment/retry UX and an independent, consented customer-email lifecycle. Do not capture partially typed contact details or treat privacy acknowledgement/cookie permission as marketing opt-in.

The follow-up scan of mounted forms found no second identical local-only submission path: canonical EOI/question and matching quiz await validated receipts; newsletter boxes open the canonical form; calculator/search forms do not claim enquiry delivery. Retained legacy modal implementations are not mounted by the main provider. **Careers has a narrower receipt gap:** `application-form.tsx` treats any successful HTTP status with parseable JSON as success, without requiring `data.ok === true`, and then clears contact fields/CV. Thus a malformed `200 {}` or `200 {ok:false}` could falsely clear an application. Harden this before enabling careers intake; the normal endpoint currently awaits staff provider acceptance. The deliberate honeypot discard is a separate anti-bot behaviour, not evidence of applicant delivery.
